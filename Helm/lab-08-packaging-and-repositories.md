# Lab 08 — Packaging & Repositories

## Objectives
- Package a chart into a versioned `.tgz` artifact
- Understand `index.yaml` and how traditional Helm chart repositories work
- Host and publish to a chart-museum-style repository
- Sign charts and verify provenance
- Practice debugging two common repo/publishing mistakes

## Prerequisites
- Labs 01–07 completed
- Helm 3.x installed
- Access to some static hosting (S3 bucket, GitHub Pages, or a local file server for practice)

---

## 1. Packaging a Chart

```bash
helm package mychart
# Produces mychart-0.1.0.tgz, named from Chart.yaml's name + version
```

This is a plain gzipped tarball of the chart directory. You can inspect it:
```bash
tar -tzvf mychart-0.1.0.tgz
```

## 2. Chart Repositories and index.yaml

A "Helm chart repository" (the traditional, pre-OCI kind) is nothing more than an HTTP server hosting `.tgz` files plus one `index.yaml` file listing them:

```bash
helm repo index . --url https://charts.example.com
```
This scans the current directory for `.tgz` files and generates `index.yaml` with metadata (name, version, digest, URLs) for each. `helm repo add`/`helm search repo` work entirely off this index file — the client never lists a bucket or directory directly.

```bash
helm repo add myrepo https://charts.example.com
helm repo update
helm search repo myrepo
```

## 3. Publishing a New Version

Adding a new chart version means: package it, then **merge** the new entry into the existing `index.yaml` rather than overwriting it:

```bash
helm package mychart          # produces mychart-0.2.0.tgz
helm repo index . --url https://charts.example.com --merge index.yaml
```
`--merge` preserves all prior entries and appends the new one. Forgetting `--merge` regenerates `index.yaml` from only what's in the local directory — a common way to accidentally wipe out history from the published index (see Troubleshooting Exercise 1).

## 4. Signing Charts and Provenance

```bash
helm package mychart --sign --key 'mykey' --keyring ~/.gnupg/secring.gpg
```
This produces both `mychart-0.1.0.tgz` and `mychart-0.1.0.tgz.prov` (the provenance file — a signed record of the chart's SHA256 digest and metadata).

Consumers verify with:
```bash
helm install demo ./mychart-0.1.0.tgz --verify --keyring ~/.gnupg/pubring.gpg
```
This confirms the chart hasn't been tampered with since signing and came from a holder of the corresponding private key.

## 5. Troubleshooting Exercise 1 — Repo Index Goes Stale After Publishing

**Scenario:** You publish `mychart-0.2.0.tgz` to your repo bucket, but `helm search repo myrepo --versions` still only shows `0.1.0`.

**Task:**
1. Confirm the new `.tgz` is actually present at the hosting URL
2. Run `helm repo update` locally — if it still doesn't show, the problem isn't client-side caching
3. Check how `index.yaml` was regenerated — if `helm repo index .` was run **without** `--merge index.yaml` in a directory that only had the new `.tgz` (e.g. a fresh CI workspace), the resulting `index.yaml` only contains `0.2.0`... but if instead the *old* `index.yaml` was blindly re-uploaded after a `--merge` step ran against the wrong working directory, you get the reverse: the new entry never made it in
4. Fix by re-running `helm repo index . --url <url> --merge <path-to-current-published-index.yaml>` against a directory containing the **full** set of chart archives (or at least fetching the current live `index.yaml` first before merging), then re-publish
5. Confirm with `helm repo update && helm search repo myrepo --versions`

**Takeaway:** `index.yaml` is a flat, hand-merged file with no server-side intelligence — any CI pipeline publishing charts needs to explicitly fetch-merge-republish it correctly every time, or track version history externally (this is one of several reasons OCI registries, covered next in Lab 09, have largely replaced this pattern).

## 6. Troubleshooting Exercise 2 — Signature Verification Failure

**Scenario:**
```bash
helm install demo ./mychart-0.1.0.tgz --verify --keyring ~/.gnupg/pubring.gpg
```
```
Error: sha256 sum does not match, .prov file was corrupted or is out of date
```

**Task:**
1. Confirm both `mychart-0.1.0.tgz` and `mychart-0.1.0.tgz.prov` are present and paired correctly (matching filenames)
2. Recognize a common cause: the chart `.tgz` was re-packaged (e.g. `helm package` run again, even with identical source content) after the `.prov` file was generated — repackaging can change the tarball's exact bytes/digest even if the logical content is the same, invalidating the old signature
3. Fix by re-signing: `helm package mychart --sign --key ... --keyring ...` in one pass, producing a matching `.tgz`/`.prov` pair, and never publish a `.tgz` that was packaged separately from its `.prov`

**Takeaway:** treat `.tgz` + `.prov` as an atomic pair generated by a single `helm package --sign` invocation — never regenerate one without the other.
